# P6/P7 第一人称研究与验收报告

- 作者：李林知
- 日期：2026-08-25
- 阶段：P6 可观测服务与可靠性、P7 Word/PDF 受控文档能力
- 结论：工程能力已完成；模型效果按开发集条件验收，不能宣称生产级完成

## 1. 我怎样定义这两个阶段

我没有把 P6 理解成“再包一层 FastAPI”，也没有把 P7 理解成“调用一个库写文件”。
P0–P5 的唯一一次冻结终测已经暴露出 multi-step 0%、recovery 0%、参数准确率偏低等
问题。如果服务只把这些错误更快地暴露给用户，项目仍然只是教学 Demo。因此我先把冻结
结果转译成可验证的系统约束，再补服务和文档交付能力：

1. 模型提前给最终答案时，编排器必须知道计划是否真的完成。
2. 参数只允许做一次可解释、可记录、通过 Schema 的保守修复。
3. 引用必须来自本轮检索结果，不能接受模型凭空写出的文档 ID。
4. 只读工具的瞬时故障可以有限重试，副作用工具不能自动重放。
5. 每个请求都要能看见路由、工具、计划、Token、耗时和结束原因。
6. Word/PDF 写入必须受路径、扩展名、大小、覆盖确认和写后校验约束。
7. 文件能被 Python 打开不等于交付合格，最终还必须逐页渲染检查。

## 2. P6：我实现的可靠性闭环

### 2.1 编排器约束

我新增了确定性的上下文预算压缩，保留 system message 和最近对话，避免无限增长的消息
直接挤爆模型窗口。对于 multi-step 路由，我把“需要调用哪些工具”变成计划完成门禁：模型
在必要工具尚未成功时提前输出 final，编排器会拒绝这个 premature final，并明确提示剩余步骤。

工具参数进入执行器前先过 Pydantic。若只是常见字段别名或包裹层级错误，我允许一次保守
修复；修复后仍不合法就失败，不用语言模型反复猜参数。这个选择降低了不可解释性，也避免
“为了成功率让系统偷偷改很多次”的指标污染。

对于超时、busy、failed to start 等瞬时错误，我只给无副作用工具一次自动重试。创建文件
等副作用工具不会自动重放，因为重复执行可能造成覆盖或多份产物。取消采用协作式 token，
在模型和工具边界检查；当前不能中断已经进入 CUDA kernel 的一次 HF generate。

### 2.2 引用边界

我用本轮 `search_docs` 的真实返回值建立 citation whitelist。最终答案若引用未出现的
`doc-*` 或 `[[citation:...]]`，会以 `citation_guard` 结束，而不是把伪引用交付给用户。
这一约束可以提高忠实性下限，但它不会替模型补上遗漏引用；“拒绝假的”与“生成完整的”是
两个不同问题，我在指标中保留了这个差别。

### 2.3 可观测服务

服务现在提供同步 `/agent/chat`、SSE `/agent/chat/stream`、取消接口、进程内聚合指标以及
本地 `/demo`。事件覆盖 route、model、tool、plan、final；响应记录 request/run ID、输入与
生成 Token、模型耗时、工具耗时、总耗时、finish reason、引用候选和已使用引用。并发信号量
默认限制为 2，避免 8GB 显存机器同时进入过多生成请求。

这里的 SSE 是阶段/进度事件流，最终模型文本在后端生成完成后出现；它还不是真正逐 Token
推送。进程内指标也不是 Prometheus 持久时序数据。这两个边界是我刻意写进验收报告的，
因为求职项目的可信度来自知道当前系统做到哪里，而不是把接口命名成 stream 就宣称完成
了生产级 streaming。

## 3. P6 真实 3B 开发集对照

我复用 Qwen2.5-3B-Instruct 4-bit + Agent v1.1 QLoRA，只替换编排可靠性层，在同一 100 条
dev 集上和 P4 保存预测做 paired comparison。P0–P5 frozen v1 没有重跑，也没有参与本轮
调参。

| 指标 | P4 保存基线 | P6 候选 | 变化 |
|---|---:|---:|---:|
| 任务成功率 | 78.00% | 79.00% | +1.00pp，paired 95% CI 0～+3pp |
| Multi-step 成功率 | 86.67%（13/15） | 93.33%（14/15） | +6.66pp |
| Multi-step 平均工具调用 | 1.20 | 1.27 | +0.07 |
| 工具选择准确率 | 86.15% | 87.69% | +1.54pp |
| JSON 合法率 | 100.00% | 100.00% | 0 |
| 参数准确率 | 80.00% | 80.00% | 0 |
| 单工具成功率 | 80.00% | 80.00% | 0，仍低于 85% 目标 |
| Recovery | 75.00% | 75.00% | 0 |
| Citation Precision | 77.78% | 76.47% | -1.31pp |
| Citation Recall | 63.64% | 59.09% | -4.55pp |
| 平均总耗时 | 5,348.78ms | 4,840.83ms | -507.95ms |

只新增一个成功转移 `ms-007`，没有任务成功回退；但 `ms-007` 同时引入一次 citation miss。
因此我不把 +1pp 描述为显著模型提升：置信区间包含 0，参数、单工具与恢复没有改善，而且
引用召回退化。更准确的结论是：计划门禁让一个多步骤案例完成，可靠性不变量和可观测性
明显增强，但模型仍需针对参数和引用完整性继续训练/评测。NF4 模型重新量化也会让单次延迟
存在波动，所以 -508ms 只能作为本机趋势，不能当作稳定性能收益。

证据：`docs/p6_agent_v1_1_3b_qlora_dev_eval.json`、
`docs/p6_3b_before_vs_reliability_v2.json`。

## 4. P7：我实现的文档 Agent 能力

我新增六个工具：`create_docx`、`create_pdf`、`read_docx`、`read_pdf`、
`summarize_document`、`export_report`。服务只有在显式配置
`MINIGPT_DOCUMENT_WORKSPACE` 后才注册它们，避免默认拥有任意文件写权限。

`DocumentWorkspace` 只接受纯文件名并限定后缀，拒绝绝对路径、父目录穿越、超过 10MB 的
输入以及未确认覆盖。创建和导出属于副作用工具，必须经过确认机制。DOCX/PDF 写出后都会
重新读取标题或正文并检查页数/结构，报告表格使用明确列宽，页脚包含作者或产品标识和页码。

为了让文件交付可复现，我增加 `scripts/export_p0_p7_report.py`，它从冻结与 P6 JSON 报告
读取指标，通过同一个工具契约生成正式 Word/PDF，而不是手工制作一份无法复跑的演示文件。

### 4.1 视觉 QA 中发现并修复的问题

第一次 PDF 在程序校验上完全通过，但逐页 PNG 显示 `STSong-Light` 的拉丁字符被查看器
替代后产生异常字距，项目名和英文术语不适合交付。我因此改成优先嵌入真实 Unicode CJK
字体，并保留无本地字体时的 CID fallback。第二次检查又发现 ListFlowable 的 bullet glyph
显示为空框，我把无序列表改成字体内明确存在的破折号段落。

最终 DOCX 为 2 页、39,702 bytes；PDF 为 2 页、126,675 bytes。两份文件的所有页面均已
以 150 DPI 渲染检查，没有发现截断、重叠、乱码或表格越界。这个过程让我确认：结构校验
解决“文件是否有效”，视觉 QA 解决“文件是否可交付”，两者不能互相替代。

新增文档依赖的下载量约 5.7MiB，远低于 40GB 上限；产物和缓存都留在 D 盘项目目录。

## 5. 工程验收

本轮新增可靠性、服务、文档和运行时测试。最终工作树的 Ruff format/lint、mypy（67 个
source files）、Dev/Frozen split validation 全部通过；全量工程测试 227 passed，覆盖率
71.36%，超过 60% 门槛。文档工具模块覆盖率 93%，编排器 94%，可靠性模块 86%。唯一警告
来自 Starlette TestClient 的上游弃用提示，与本阶段功能无关。

## 6. 当前不足与下一步

- SSE 尚未做到 Transformer 逐 Token streaming，取消也不能抢占一次进行中的 GPU kernel。
- 聚合指标只在单进程内存中，缺少 Prometheus、持久化 trace 和跨进程聚合。
- 没有长期记忆、用户隔离、鉴权、速率限制和生产级 secret 管理。
- citation whitelist 能拒绝伪造来源，但不会提高检索触发或补齐漏引用。
- P7 面向结构化报告，不支持任意复杂 Word 模板编辑、批注修订、OCR 或扫描件理解。
- P6 只做 dev 对照，P0–P5 frozen v1 仍保持唯一一次运行结果；要宣称新版本冻结提升，必须
  先定义新候选和新验收规则，而不是反复查看旧 frozen 后继续调参。

我的下一优先级不是下载更大的语料或立即进入多模态，而是建立 token-level streaming、
更困难的参数/引用 dev 集和服务负载基准。P8 再做从零训练线现代化，P9 才扩展图像与语音。
